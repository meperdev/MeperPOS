# Purchase order documents

Objective: turn a purchase order into a document the business sends to its supplier: a letter-size PDF built from a per-business template, a two-step confirm-and-send action, an expected delivery date with overdue tracking, and "repeat order" from the history. Receiving and stock integration stay as they are.

Branch: `feat/purchase-order-documents` (worktree `../MeperPOS-worktrees/purchase-order-documents`, from `master` `fa79f06`).
Delivery: ask-on-risk → stacked PRs to `master` (user choice, 2026-11-18); one branch per slice, each PR based on the previous slice.
Test runner: `cd backend && npx jest <path>`; `cd frontend && npx vitest run <path>`.

## Specs

- **S1** — User intent (verbatim): "un lugar donde yo puediera generar las "facturas" o bien dicho ordenes de compra relacioandas con el proveedor y tuveiera una forma sencilla de enviarle eso al proveedor sea al descargar el pdf o en el futruro con meper intelligence". A confirmed order produces a letter-size PDF (not the thermal receipt width) with, top to bottom: business logo, name, NIT, phone and address; title `Orden de compra OC-<n>` with issue date and expected delivery date; supplier name, NIT, contact, phone and email; item table (product, quantity, unit cost, tax, line total); subtotal, tax and total as stored on the order; the order notes; the business template fields (S2); "Elaborado por". Every amount comes from the stored order; the renderer derives no totals.
- **S2** — "una plantilla por negocio de su orden de compra". A new settings section, `Ajustes → Órdenes de compra`, stores per organization: delivery address (defaults to the business address when empty), payment terms, terms and conditions, and footer — all free text. It shows a live preview, like the invoicing section. Order-specific exceptions go in the order notes; orders get no per-order template fields.
- **S3** — "Confirmar y enviar, pero en el mismo lugar, pero en dos pasos" / "ambos botones pegados (unidos, pero separados, me entiends?)". One modal holds a joined button group `[ Confirmar | Enviar ]`. Confirmar does what confirm does today (DRAFT → PENDING). Enviar is enabled **when the server answers that the confirmation succeeded** — agreed replacement for "a los 3seg le habilita el boton de enviar", because a fixed timer can enable sending an order whose confirmation failed. The transition is visible (Confirmar becomes "Confirmada", Enviar lights up). The same modal has an optional expected delivery date, sent with the confirmation.
- **S4** — Sending downloads the PDF and records the send instant and channel (`PDF` now; `WHATSAPP` reserved for Meper Intelligence). No new status: the order stays `PENDING`, and the badge reads "Enviada" when it has a send instant. Receiving, the "Por recibir" filter and the daily report keep working unchanged. Closing the modal after confirming leaves the order confirmed and "sin enviar"; Enviar stays available on the detail page. Re-sending is allowed any time and keeps the first send instant.
- **S5** — At the first send the server stores a fixed snapshot of the business data, the supplier data and the template. Every later PDF download of a sent order renders from that snapshot, so it is the same document the supplier received even if settings or the supplier change. Items and totals are already immutable after confirm and are not copied.
- **S6** — An order is overdue when its status is `PENDING` or `PARTIAL_RECEIVED`, it has an expected delivery date, and that date is before today in Colombia time. The server computes the `overdue` field; the list shows an "Atrasada" badge and the status filter offers "Atrasadas".
- **S7** — "mantener un hidtorial de ordenes de compra" / "poder usar uno igual solo alterar". The existing list is the history. Every order detail, in any status, has "Repetir pedido": the server builds a new draft with the same supplier, products and ordered quantities, using each product's current cost and tax rate; it leaves out inactive or deleted products and services and reports which were left out. The user lands on the new draft with the editor open.
- **S8** — "repetirias el mimso pedido apesar de haber seleccionado a otro proveedor distinto del ultimo pedido creado?". "Repetir pedido" opens a small modal with a supplier select preselected with the source order's supplier; choosing another supplier creates the draft for that supplier, and the modal then shows "Revisa los costos: son los de la última compra." (neutral register of the approved "Revisá los costos, son los de la última compra", per the UI copy convention).
- **S9** — "todo eso de validar e intefrar al stock que ya hace hoy me sigue sirviendo". Receiving, the stock compare-and-swap, the `OC-<n>` inventory movement and the cost audit stay untouched. New endpoints use the roles that can confirm today.
- **Out of scope**: WhatsApp or email sending, named order templates.
