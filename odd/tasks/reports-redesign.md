# Reports redesign + daily report + Economía fixes

Objective: turn `/reports` into a clearer reports page with a "Hoy" daily-report section, fix the audited Economía calculation gaps, and redesign the analysis blocks.
Branch: `feat/reports-redesign` · Delivery: `single-pr` ("TOdo junto, solo separada por commits") · Runners: backend `npm run test -- --testPathPatterns=<file>` (Jest 30, Postgres on 5432 is up), frontend `npx vitest run <file>`.

## Specs

- **S1 — Daily report on the page.** User: "Tambien me interesa el generador del reporte diario que se usaria para el intelligence usarlo para poder generar el reporte diario ahi mismo en la pagina de reports." Chosen option: "Opcion 1 si", meaning **view it on screen and download it**: a "Hoy" section fed by `GET /api/reports/daily-report` (pulse: sales total and count, expenses, cutoff time, refresh; pending items with counts, the first 3 and a link: low stock → `/inventory?filter=lowStock`, pending purchase orders → `/purchase-orders?status=OPEN` (see L11), overdue or due loans → `/loans`; a collapsible list of today's sales with number, time, customer and total) plus a "Reporte del día (PDF)" button using `GET /api/reports/daily-report/pdf`. It always shows today, independent of the period filter, and says so. The backend daily report is reused unchanged.
- **S2 — Page structure** (approved: "Me sirve"): header (PDF button and a direct export button; the export strip that rendered `( → )` is removed) → Hoy → Análisis del período, with the period filter placed above Análisis because it only applies there. Análisis = Economía, Caja e inventario, Ventas (top products, categories, customers, payment methods) + **ventas por vendedor** (`GET /api/reports/users/performance`, currently unused).
- **S3 — Visualizations.** User: "mira opciones de mostrar la info [Image 1] distinta a esa, me gusta esa, pro no para todos los graficos". Agreed mapping: top products = ranked bar list (the style the user likes); categories = one 100% stacked bar + legend sorted desc (top 5 + "Otras"); payment methods = one segmented bar + figures, without $0 rows; top customers = compact table of 5 without the walk-in bucket; new "Ganancia por producto" table from the existing `products[]` margins; ventas por vendedor = table (sales, total, average ticket).
- **S4 — No floating cards.** User: "mira que las cards no queden medio volando con informacion que nunca se llenara porque es minima." Cards size to their content (no stretching to match a neighbour); a block that rarely fills becomes one line of text or merges with another block.
- **S5 — Economía audit fixes.** User: "quiero que solicites los calculos de Economia y revises tu personalmente como estan y si hay algun hueco o mejora para ellos." Fix each audited gap with a test:
  - S5.1 Expense dates (stored at UTC midnight) filtered with the Bogotá timestamp window — probable off-by-one day; confirm with a RED test first (`expenses.service.ts` `findForReports`; also check `ExpensePayment.date` in cash flow and the economic export).
  - S5.2 "Todo" means current month in Economía but all time in the operational reports — the page always sends an explicit range (default "Este mes").
  - S5.3 Delta percentage divides by a signed previous value (inverted sign when previous < 0) and reports 100% when previous = 0 — use |previous|, and `null` when previous is 0 and current is not.
  - S5.4 The breakdown does not reconcile when items lack a cost snapshot — expose `attributableRevenue` and make the breakdown add up.
  - S5.5 Operational reports (top products, categories, payment methods, customers) drop `RETURNED_PARTIAL` sales entirely while Economía nets returns — make them consistent.
  - S5.6 Net cash flow is computed in the browser (`page.tsx:626`) — the server returns `netFlow`.
  - Also: categories sorted by total desc; the walk-in "Guest" bucket (sales without a customer) is excluded from the top customers ranking.
- **S6 — Design rules.** User: "recuerda que todo el frontend tiene que llevar reglas de la skill unslop-ai-ui e impeccable que tengo en el sistema. Tu tambien ayudame con el front, pero sin salirse como del diseño central". Stay inside the existing design system (tokens in `globals.css`, `SectionShell`, `MetricCard`, `Table`, `cn()`, `formatCurrency`), sentence case Spanish copy, `tabular-nums`, no pills/emoji, 4/8px grid. Run the impeccable detector on the changed UI.
- **S7 — Delivery.** User: "TOdo junto, solo separada por commits" — one PR, one Conventional Commit per work unit.

- **S8 — Expenses page layout.** User: "El input y toda la zona en general de Salidas se ve mal." Summary metrics as one full-width strip (no half-width cards leaving empty space); one filter toolbar where search, month, label, supplier and status controls share one height and align on one row on desktop and wrap cleanly on phones; expense cards on the shared collection grid.
- **S9 — Hoy pending groups.** User: "Me gustaria que topda esa informacion de Productos con stock bajo, Órdenes de compra, Préstamos, etc. SE visualicen mejor y se l epuede añadir alguna key o chip." Each pending group becomes a card (icon, label, count, link to the filtered page) with its first items as neutral chips carrying a key value and a 6px status dot (stock: out of stock vs under minimum; purchase orders: pending vs partially received; loans: overdue vs due soon).
- **S10 — Analysis layout by size.** User: "quiero que las cards esten junto a cards de su mismo tamaño". Caja y pagos full width (cash in/out/net + payment methods); Inventario actual full width (4-cell strip); Productos más vendidos ‖ Ganancia por producto; Categorías full width; Mejores clientes ‖ Ventas por vendedor; paired cards stretch to equal height.
- **S11 — Alerts history access and design.** User: "NO tengo como acceder a la pagina de historial de notificacin que no sea por parte de la propia notificacion, seria adecuado dejarle alguna acceso desde los tres botones? asi como MI perfil y configuracion? Y tambien mejorarla un poco siento que se hizo de rapidez, aplicarle mas diseño como el actual." Add the alerts history to the account menu (desktop and phone) for the roles that may open `/alerts`; redesign `/alerts` in the current design language without changing the backend contract.
- **S12 — WhatsApp daily report attempts.** User: "Wpp no tiene limite con los intentos, entonces ajustarlo y generar algo como para resetear o no se que opcion sea mejor para mantener lo que importa y no ver tanto falló". Decision (parent): (a) a scheduled run with no recipient creates no delivery row and the page shows the automatic send as paused for that reason; (b) after 3 consecutive failed scheduled deliveries with no successful delivery since, the scheduler pauses (no row) until a successful send; the manual send is the resume action; (c) a read-only endpoint reports the automatic state; (d) the history groups consecutive identical failures into one row and shows the most recent groups first; existing rows are never deleted.
- **S13 — Settings General.** User: "tambien haz que general se sienta mejor, no dos lineas y un mini cuadro apra la foto xd". Redesign the General settings section (business name + logo) with a real logo area and a receipt-header preview, using only the existing fields and endpoints.

- `GET /reports/sales/category`: `data` sorted by total desc.
